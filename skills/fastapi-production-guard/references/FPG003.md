# FPG003 — balance read and written without serialising requests

**Invariant:** whatever reads a balance to decide whether a spend is allowed
holds a lock that every other writer of that balance also takes — or the
check and the write are one SQL statement.

## The bug, in three shapes

```python
# A counter: read, modify, write.
if user.credits < cost:
    raise HTTPException(402)
user.credits -= cost
await db.commit()
```

```python
# A ledger: check, then insert.
balance = await get_balance(db, user.id)        # SELECT SUM(delta) ...
if balance < cost:
    raise HTTPException(402)
db.add(CreditTransaction(user_id=user.id, delta=-cost))
```

```python
# An atomic UPDATE behind a stale check.
if user.credits < cost:
    raise HTTPException(402)
await db.execute(update(User).where(User.id == user.id).values(credits=User.credits - cost))
```

Two requests that arrive together both read "1 credit left", both pass, both
spend. The counter also loses updates: twenty spends can succeed and lower
the balance by one. Under READ COMMITTED — the default in Postgres and MySQL
— nothing in the database stops any of this.

## The fixes

**Lock the owner's row before reading**, in every function that writes the
balance (spend, grant, expire, refund):

```python
await db.execute(select(User.id).where(User.id == user_id).with_for_update())
balance = await get_balance(db, user_id)
if balance < cost:
    raise InsufficientCredits()
db.add(CreditTransaction(user_id=user_id, delta=-cost, job_id=job_id))
```

Or an advisory lock keyed on the owner:
`await db.execute(text("SELECT pg_advisory_xact_lock(:k)"), {"k": user_id})`.

**Or make the check part of the write**, and read the row count:

```python
result = await db.execute(
    update(User)
    .where(User.id == user_id, User.credits >= cost)
    .values(credits=User.credits - cost)
)
if result.rowcount == 0:
    raise InsufficientCredits()
```

- A lock helps only if **every** writer takes it. A grant or an expiry that
  reads the balance without the lock races the spends that take it.
- Compute derived values (the excess to expire, the amount to refund)
  **after** taking the lock, not before calling the function that takes it.
- `asyncio.Lock()` and `threading.Lock()` serialise one process. Production
  runs several workers, so they do not count.
- For anything you bill for, prefer an append-only ledger (one INSERT per
  movement, balance derived with `SUM`) plus a unique key per job, so a
  retried job cannot spend twice either.

## What the rule looks for

In every function outside tests: a read of a balance-like value — an
attribute (`user.credits`, `wallet.balance`, `quota_remaining`), a function
that returns one (`get_balance()`, `remaining_credits()`), or a SQL
`func.sum(...)` over an amount — followed by a write that depends on it:
an assignment back to the field, a ledger row built from it or after
checking it, an UPDATE behind a check it does not repeat, or the value
passed on to a function that writes balances. It reports when nothing before
the read locks the row: no `with_for_update` / `FOR UPDATE`, no `lock_*()`
helper, no advisory lock, no SERIALIZABLE isolation, no `version_id_col`
optimistic locking on the model.

Request schemas and other non-table classes are skipped when the code says
what they are (`body: SpendRequest`), and functions with no database session
in sight are skipped as in-memory arithmetic.

## Confidence

- **high** — a read and a dependent write in the same function with no lock.
- **medium** — a balance read without a lock whose result is handed to
  another function that writes balances (stale input), or a read-modify-write
  inside a model method, where the lock belongs to whoever loaded the row.

## Proving it

The `[[race]]` probe reads the balance, fires N identical spends at the same
instant, reads it again, and fails when more spends succeeded than the
balance paid for, when it went negative, or when it fell by less than the
successes cost (lost updates). See [probes.md](probes.md).

## Reference implementation

[The Fabrica](https://docs.thefabrica.dev/production/credits?utm_source=fastapi-production-guard&utm_medium=rule-doc&utm_campaign=FPG003)
keeps credits as an append-only ledger with a `UNIQUE(job_id, kind)` key and
a `FOR UPDATE` lock on the owner's row, with the concurrency test that
proves it.

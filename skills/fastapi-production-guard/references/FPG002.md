# FPG002 — webhook side effects without deduplication

**Invariant:** a webhook handler claims the provider's event id, atomically,
before it does anything a retry would repeat.

## The bug

Every provider delivers at least once. Stripe retries for up to three days,
Paddle for longer, Svix (Clerk, Resend) on any non-2xx answer — and a
timeout on *your* side counts as a failure even when your code finished.
A handler that grants credits on every delivery grants them on every retry:

```python
@router.post("/webhooks/stripe")
async def stripe_webhook(request: Request, db: DB):
    event = stripe.Webhook.construct_event(await request.body(), sig, secret)
    if event["type"] == "checkout.session.completed":
        db.add(CreditGrant(user_id=..., amount=500))   # once per delivery, not once per payment
    await db.commit()
```

## The fix

Insert the event id into a table with a UNIQUE constraint, in the same
transaction as the side effects, and stop when the insert conflicts:

```python
class ProcessedEvent(Base):
    __tablename__ = "processed_webhook_events"
    id: Mapped[int] = mapped_column(primary_key=True)
    provider: Mapped[str] = mapped_column(String(16))
    event_id: Mapped[str] = mapped_column(String(128))
    __table_args__ = (UniqueConstraint("provider", "event_id"),)


@router.post("/webhooks/stripe")
async def stripe_webhook(request: Request, db: DB):
    event = stripe.Webhook.construct_event(await request.body(), sig, secret)
    claim = await db.execute(
        insert(ProcessedEvent)
        .values(provider="stripe", event_id=event["id"])
        .on_conflict_do_nothing()
    )
    if claim.rowcount == 0:
        return {"duplicate": True}          # 200: tell the provider to stop retrying
    ...                                     # side effects, same transaction
```

Equivalent, if you prefer the ORM: `db.add(ProcessedEvent(...))`, `await
db.flush()`, and on `IntegrityError` roll back and return 200.

- **Use the provider's event id**, not a hash of the body: Stripe
  `event["id"]`, Paddle `payload["event_id"]`, Svix/Clerk/Resend the `svix-id`
  header, GitHub the `X-GitHub-Delivery` header, Standard Webhooks (Polar)
  the `webhook-id` header.
- **Same transaction.** If the claim commits and the side effect fails, the
  retry is skipped and the work is lost. If the side effect commits without
  the claim, it runs twice.
- **Queued work** (`task.delay(payload)`) moves the problem, it does not
  remove it: the task must claim the id, or the handler must claim it before
  enqueueing.
- **A SELECT first is not enough.** `if await db.get(ProcessedEvent, id):
  return` followed by an insert lets two simultaneous deliveries both pass.
  It is safe only when the UNIQUE constraint backs it up and the conflict
  rolls the side effects back.

## What the rule looks for

A POST route that is an incoming webhook — `webhook`/`hook` in its path or
name, a provider signature header, or a signature-verifying call — and has
no user dependency (a route that identifies a user *manages* webhooks and is
skipped). From it, the rule follows your own code: helpers, services,
methods on module-level service objects, handler tables, background tasks
and `.delay()`ed jobs. It accepts:

- `on_conflict_do_nothing` / `on_conflict_do_update`, `INSERT ... ON
  CONFLICT`, `INSERT OR IGNORE`, Redis `SET ... NX`, or a helper whose name
  says so (`create_on_conflict_do_nothing`), next to the event id or a table
  named for events;
- an `except IntegrityError` (or `UniqueViolation`) next to the event id;
- a lookup of the event id followed by an early return, **if** the table
  has a UNIQUE constraint on the event id.

## Confidence

- **high** — no deduplication, and the reachable code does something that
  repeats on a retry: inserts a row, enqueues a job, sends a message, grants
  or charges.
- **medium** — a check-then-insert with no unique constraint behind it; or
  the only effects recognised set state (`update`, `mark_failed`). A handler
  whose every effect is safe to repeat may be suppressed, with that reason.

## Proving it

The `[[webhook]]` probe signs a real event the way the provider does, sends
it, re-signs and sends it again with the same event id, then sends two copies
of a new event at the same instant — and checks that a value the event
changes moved exactly once each time. See [probes.md](probes.md).

## Reference implementation

[The Fabrica](https://docs.thefabrica.dev/production/webhook-delivery?utm_source=fastapi-production-guard&utm_medium=rule-doc&utm_campaign=FPG002)
runs Paddle and Clerk deliveries through one claim table and an archive, so
a replay is a no-op and a failed delivery can be replayed by hand.
